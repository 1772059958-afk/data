## exp-20261023-01 · 2026-10-23 · 五组对照首次联调（4 实例 × 5 组 + ESC）

**目的**：验证 A/B/C/D/E 五组对照的**通路能否在真实实例上全部通电**——
假设：共享前缀、固定延续、受限交互、四路路由可以在同一套代码上跑完并被官方 harness 判分。
（注意：这不是"哪组更强"的假设，n=4 无法支撑。）

**变量**
- 自变量：前缀之后的走向（A 固定延续 / B 全程交互 / C 全部升级 / D 证据路由 / E 随机 p=0.5）
- 因变量：resolved（官方 harness 判定）、能耗（CNY、模型调用数、工具调用数）
- 控制：模型 `deepseek-flash`、thinking=on、effort=low、`max_tokens=16384`、前缀候选数 2、
  交互上限 6 次模型调用 / 10 次工具调用、停滞容忍 3、五组共用同一前缀与同一预算档

**设置**
- 数据集：SWE-bench Lite `dev`，4 个金标准可解实例（`data/harness/dev.parquet`）
- 配置：`configs/frozen_v1.json`（version=`frozen_v1`）
- 路由阈值：`u_loc=0.50`、`u_dup=0.50`，**占位值、未校准**（见 `docs/实验协议_v2.md` §6）
- 代码：本仓库 `src/swe_repair/{prefix,interact,cf,router,state,budget,spend}.py` + `scripts/run_cf.py`
- 环境：WSL2 Ubuntu 24.04 + Docker 29.1.3 + `swebench` 5.0.2（venv `/opt/swe-env`）
- 种子：`--seed 20261023`
- 复现命令：
  ```
  /opt/swe-env/bin/python scripts/run_cf.py --interactive-calls 6 --interactive-tools 10 \
      --max-tokens 16384 --tag cf_dev4 --total-cny 7.5 --per-instance-cny 2.2
  /opt/swe-env/bin/python work/split_preds.py cf_dev4
  bash work/score_all_arms.sh cf_dev4
  /opt/swe-env/bin/python scripts/analyse_cf.py --tag cf_dev4
  ```

**结果**

生成总花费 **1.2096 CNY**（`reports/cf_dev4_matrix.json` → `spent_cny`），4 个实例含两条分支与 B 组，
单实例均值 0.302 CNY。

| 实例 | 前缀 | A 固定 | ESC 交互 | B 单独 |
|---|---|---|---|---|
| marshmallow-1343 | resolved | resolved | empty | empty |
| astroid-1196 | empty | empty | resolved | empty |
| astroid-1978 | unresolved | unresolved | empty | unresolved |
| sqlfluff-1625 | unres. | unresolved | unresolved | empty |

各组 resolved（`reports/cf_dev4-<arm>.cf_dev4.json`）：
**A=1, B=0, C=2, D=2, E=1, ESC=1**（分母 4）。

四象限（`reports/cf_dev4_analysis.json`）：Q1 双重成功=0，Q2 仅固定成功=1，
Q3 仅交互成功=1，Q4 双失败=2；**升级必要占比 = 0.25**。

策略对照（同文件 `policies`）：A=1/4、C(全升级)=1/4、oracle=2/4、D=2/4、E=1/4；
神谕缺口闭合率 **1.0**（headroom=1, gained=1）。

组间一致性：**C 与 D 逐实例决策完全相同**（各 3 次升级）；E 与 C 不同（1 次升级）。

**观察**（不含解释）
1. 五个臂与 ESC 均产出补丁并被判定，其中 3 个臂存在空补丁（ESC 2 个、B 3 个、A 1 个）。
2. `marshmallow-1343` 前缀就已有 2 个候选通过公开测试，四组在此实例全部走"冻结"。
3. `astroid-1196` 前缀 0 个候选可应用，A 组补丁为空，ESC 组 20 行补丁被判 resolved。
4. `astroid-1978` A 组有 11 行补丁且未解决；ESC 为空；C/D/E 提交的是 ESC（空）。
5. `sqlfluff-1625` A 与 ESC 都有补丁，均未解决。
6. 交互分支从未自行调用 `finish`；两个批次分别以 `model_call_budget` / `tool_budget` 结束。
7. B 组 4 个实例中 3 个空补丁，唯一非空补丁在 `astroid-1978` 且未解决。
8. 首轮 smoke（`reports/cf_smoke1_matrix.json`）四组决策全为 `stop`、五个补丁全空。

**本次过程中定位并修正的缺陷**（每条都有失败现场或实测数字支撑）

| # | 缺陷 | 证据 | 修正 |
|---|---|---|---|
| 1 | 交互执行器调用模型时未传 `tools` | 代码审查 `interact.py` | 每次请求带 `tools=tool_choice="auto"` |
| 2 | `run_one` 把 `RepairState` 当 `RouterConfig` 传入 | `NameError`/`AttributeError` | 显式传 `cfg` |
| 3 | `checks_run` 从不写入 → `behavioural_signal()` 恒为 `"none"` | 首轮 smoke `signal=none` | 校验后回写 `checks_run`/`registered_test_commands` |
| 4 | 预算档 `small=32000 token` 小于一个前缀 | 实测前缀 **47009 token**，A/C/D/E 决策全 `stop` | 改为 demo 档 `200000 token`（协议 v2.1） |
| 5 | 上下文按词法路径优先，模型定位的目标文件被挤出 | 模型改 `schema.py` 却从未读到它，`n_applicable=0` | 模型定位文件优先入读 |
| 6 | 补丁 `@@` 行数未修正 | 首轮 2 个候选均 apply 失败 | 抽出 `patchutil.repair_hunk_headers` 统一修正 |
| 7 | 升级分支种子不含文件正文 | 交互组 8 次工具调用 0 补丁 | 种子带上与固定分支相同的文件内容 |
| 8 | 交互提示无具体预算数字 | 同上 | 会话内显式写出调用上限与"最多 2 次分析后打补丁" |
| 9 | 跳过 B 组时仍写空补丁行 | 分析会把空补丁计入 B 的失败 | 跳过时不写该行 |
| 10 | 容器名用 `hash()`，进程间加盐 | 不可复现 | 改确定性 slug |
| 11 | 分析脚本按 `<tag>*` 匹配报告名 | harness 实际命名 `<model>.<run_id>.json`，一个都读不到 | 改为按 `.{tag}` 切分 |

**结论**：**支持**"五组通路可全部通电"（五组均产出补丁并被判分）。
对于核心主张——前缀证据能否预测升级价值——**不确定**：n=4、正例 1，任何 AUC 都无统计意义；
且 C 与 D 决策完全相同，说明当前规则集**在结构上无法区分**级联与自适应。

**下一步**
1. 修规则集：`interactive_when_no_behavioural_signal` 在"前缀无公开通过候选"时恒触发，
   使 D 必然等于 C。需与导师确认改法（见 §"待决策"），改前不跑主实验。
2. 把 n 从 4 提到 98（已下载镜像的 test 子集），否则 AUC 与神谕缺口闭合率都不可解释。
3. 交互分支要能自行 `finish`：当前 8 次 smoke 与全量运行中一次都没有主动收尾。

## exp-20261023-02 · 2026-10-23 · 信号链接通后的 7 实例对照（协议 v2.2）

**目的**：验证"把公开测试失败分类写进状态机"（协议 v2.2）之后，D 组是否终于能与 C 组产生分歧。
假设：有了 `behaviour_assertion` 记录，`behavioural_signal()` 会返回 `behavioural`，规则 7 不再无条件触发，
D 在部分实例上会选择"固定"。

**变量**
- 自变量：协议版本（v2.1 无失败记录 / v2.2 有失败记录）
- 因变量：D 与 C 的决策分歧率、神谕缺口闭合率、各规则触发分布
- 控制：同模型、同参数、同前缀候选数 2、同交互上限（6 次调用 / 10 次工具）、同占位阈值 0.50

**设置**
- 实例：7 个（`marshmallow-1343/1359`、`astroid-1196/1866/1978`、`sqlfluff-1625/2419`），全部来自 dev 金标准可解子集
- 新增代码：`prefix.run_public_tests` 返回原始输出；`validate_candidate` 用 `FailureRecord.from_output(stage="test")`
  分类入账；`run_cf` 把 `router.evaluate_all` 全表写入矩阵；回归测试 `tests/test_signal_chain.py`（6 项）
- 离线测试：**167 项全过**
- 复现命令：
  ```
  /opt/swe-env/bin/python scripts/run_cf.py --instances <7 ids> --interactive-calls 6 \
      --interactive-tools 10 --max-tokens 16384 --tag cf_dev7_v22 --total-cny 6.0
  /opt/swe-env/bin/python work/split_preds.py cf_dev7_v22
  bash work/score_all_arms.sh cf_dev7_v22
  /opt/swe-env/bin/python scripts/analyse_cf.py --tag cf_dev7_v22
  ```

**结果**

生成花费 **1.3445 CNY**（7 实例，含两条分支与 B 组）。

各组 resolved（分母 7）：**A=3, B=1, C=3, D=3, E=3, ESC=1**。
四象限：Q1=0、Q2=**3**、Q3=1、Q4=3；升级必要占比 0.143。
oracle=4/7；**神谕缺口闭合率 = 0.0**（D 相对 A 增益为 0）。

D 与 C 的逐实例决策**仍然完全相同**（各 5 次升级）。

规则触发分布（`reports/cf_dev7_v22_analysis.json` → `rule_firings`）：
- 实际决定 D 的规则：`freeze_when_public_candidate_passes` 2 次、
  `interactive_on_wide_localization_disagreement`（规则 4）**4 次**、
  `interactive_when_no_behavioural_signal`（规则 7）1 次
- 若不短路，会触发的次数：规则 4 **6 次**、规则 7 5 次、`fixed_continuation_otherwise` **7 次**

特征 AUC（n=7，正例 1）：`n_applicable`=1.00、`u_dup`=1.00、`lacks_behavioural_signal`=0.667、
`n_public_pass`=0.667、`u_loc`=**0.167**。

**观察**（不含解释）
1. v2.2 生效：`marshmallow-1343` 的第二个候选分类为 `behaviour_assertion`，该实例 `signal=behavioural`。
2. 其余 5 个实例 `signal` 仍为 `none`：其候选的 `validation` 是 `not_applicable` 或 `not_run`，
   `checks_run=0`，**没有任何检查被执行**，因此没有失败可分类。
3. `public_test_files` 只在 marshmallow 找到测试文件；astroid 与 sqlfluff 全部 `not_applicable`。
4. `astroid-1196` 两个候选的 diff 没有 `--- a/` 文件头（`reply_head` 直接以 `@@` 开始），`extract_patch` 返回空。
5. 交互分支 7 个实例中 **6 个交空补丁**（`Instances with empty patches: 6`）。
6. 于是"全升级"的 C 从 A 的 3/7 掉到 **1/7**，D 也只能维持 3/7。
7. 决定 D 的规则从规则 7 转移到规则 4（4/7），但两条路线都通向"升级"，分歧率仍为 0。

**结论**：**否定**假设——v2.2 没有让 D 与 C 分开。
同时也否定了一个更早的判断：**当前瓶颈不是路由规则，而是执行器交不出补丁**。
Q2=3 说明有 3 个实例上"固定分支本来能修好，一升级就变成空补丁"，这是执行器缺陷，与路由无关。

**下一步**
1. 修交互执行器的收尾：预算耗尽时用一次**无工具**调用强制产出补丁。这是消灭 6/7 空补丁最直接的办法。
2. 修公开测试发现：目前只找与模块同名的 `test_<stem>.py`，astroid/sqlfluff 的测试布局完全不匹配。
   不修这条，`behavioural_signal` 在大部分仓库上永远是 `none`。
3. `u_loc` 暂不可作为路由依据：它在这 7 个实例上饱和（多为 1.0）且 AUC=0.167（反向）。
   需先确认"词法 vs 模型"这种构造本身是否有意义，再谈阈值。
4. `astroid-1196` 提示提示词需要明确要求 diff 带文件头；`extract_patch` 也可加一条兜底（无头 hunk 时用定位文件补头）。

**待决策（更新）**
- 规则 4 在该样本上反向有效：是**换构造**（例如改用多次模型定位之间的分歧，而不是"词法 vs 模型"），
  还是**降级为次要规则**？这属于方法设计判断，需导师定。
